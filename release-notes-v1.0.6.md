# Teleproxy.Keenetic 1.0.6 (кандидат на проверку)

Дата: 2026-11-08

## Что исправлено

**Эвикция соединений при заполнении пула буферов.** Когда пул занят больше чем
на 3/4, teleproxy закрывает соединения, чтобы освободить буферы. Раньше очередь
эвикции обновлялась только при создании соединения (`lru_insert_conn` вызывался
на accept), поэтому «самым старым» оказывалось не простаивающее соединение, а
долгоживущее — то самое, через которое идёт видео к DC Telegram. В результате
под нагрузкой рвались рабочие соединения: картинки и видео открывались рывками,
хотя процесс и канал были исправны.

Что изменено в `src/mtproto/mtproto-proxy.c`:

- в `struct ext_connection` добавлены `last_active` и `last_bytes`;
- новая функция `update_conn_activity()` вызывается из `cron()` раз в секунду:
  обходит список соединений и отмечает время, когда у соединения менялся объём
  занятых буферов (это и есть признак жизни);
- `check_all_conn_buffers()` теперь выбирает жертву не по голове LRU-списка,
  а по минимальному `last_active`, то есть закрывает то соединение, которое
  дольше всех молчит и при этом держит буферы;
- срабатывание эвикции, помимо старого условия «занято > 3/4 байт», теперь
  включает и настоящее исчерпание пула: `allocated_buffer_chunks >=
  max_buffer_chunks`. Аллокатор отдаёт память чанками по 2 МБ, и когда все
  чанки выделены, очередной `alloc_msg_buffer` падает с `cannot allocate tcp
  receive buffer` — хотя по байтам занято может быть меньше 3/4 (фрагментация
  по классам размера). Именно поэтому прежняя эвикция не срабатывала, хотя пул
  был полон. При таком срабатывании закрывается одно соединение за тик, чтобы
  клиенты успевали вычитать данные;
- при создании соединения `last_active = precise_now`, `last_bytes = -1`.

Всё в engine-контексте (`cron`), без изменений в net-cpu-хуках — на 124 МБ
роутере это принципиально: никаких новых блокировок и обращений к спискам из
сетевого потока.

## Пул буферов: 10 МБ по умолчанию

`init/S99teleproxy` теперь запускает прокси с `--msg-buffers-size 10485760`.
Чанк буферов — 2 МБ (`MSG_BUFFERS_CHUNK_SIZE`), то есть это 5 чанков вместо 4.
Причина: 8 МБ под видео упирались в потолок (`allocated_buffer_bytes` ровно
8 388 352 = 4 чанка), а чанк выделяется целиком — стоило попросить пятый, как
эвикция начинала рубить соединения. 10 МБ даёт запас, `available` на Viva
остаётся ~20 МБ. 16 МБ по-прежнему не рекомендуются (kswapd/OOM).

Тот же дефолт прописан в `S98teleproxy-fw` (`POOL_DEFAULT`) и в комментариях
`config.toml.example`.

## Обратное давление в relay (главное)

Тест 2026-11-08 13:00–13:02 показал: пул дошёл до 5/5, `connections_failed_lru`
остался **0** — эвикция по LRU в этом режиме не срабатывает (список, по
которому она ходит, пуст), и прокси просто перестал принимать соединения,
после чего сторож перезапустил его через три минуты.

Поэтому вместо «убивать по нехватке» добавлено обратное давление:
`tcp_direct_relay` проверяет `allocated_buffer_chunks` и, если пул выбран
**полностью**, ставит `C_STOPREAD` на соединение и снимает его через 20 мс
(`relay_backpressure`, тот же механизм, что у `rate_limit_after_relay`).
Прокси перестаёт читать из DC, пока клиент не вычитает очередь; перезапуск не
нужен. Работает в обе стороны (client→DC и DC→client).

Важно про порог: сперва он был «осталось меньше одного чанка», и на пуле 10 МБ
это срабатывало уже на 4/5. В результате прокси почти всё время стоял в
паузах: сервер упирался в окно получателя (`bw 4,7 Мбит/с` против
`delivery_rate 98 кбит/с`, `rwnd_limited 39.8%`), и видео «не грузилось» при
незаполненном пуле. Поэтому порог сдвинут на «пул выбран полностью», а пауза
укорочена до 20 мс. Наблюдение — 2026-11-09, жалоба «с сотового видео не
грузится».

## Сторож и лимиты

- `S98teleproxy-fw`: цикл 20 с вместо 60; перезапуск **только если трафик
  встал**, а не просто при высоком пуле. Наблюдение 2026-11-09: сторож рубил
  teleproxy каждые 20–30 минут при «пул 99%», хотя данные шли, — из-за этого
  видео «замирало» на ровном месте. Теперь условие: пул ≥95% **и** за цикл не
  прочитано ни байта, два цикла подряд (либо пул ≥85% и простой три цикла);
- `S99teleproxy`: `--max-special-connections 48` вместо 32 (в тесте два
  телефона давали 28 из 32).

## Что НЕ менялось

- `--connections 128`.
- `postinst`, формат конфига и статистики.

## Проверка

```sh
opkg install /opt/tmp/teleproxy-keenetic_1.0.6_mipsel-3.4.ipk
curl -s http://127.0.0.1:8899/stats | grep -E 'connections_failed_lru|allocated_buffer_bytes|active_connections'
```

Под нагрузкой (видео, несколько устройств) `connections_failed_lru` должен
расти заметно медленнее, чем на 1.0.5, а обрывы — приходиться на простаивающие
соединения.

Сообщение об эвикции пишется через `vkprintf (2, ...)`, а `verbosity` по
умолчанию 0 — то есть в логе его **не будет**, пока не добавить `-v 2` в
`EXTRA`. Для проверки это не обязательно: смотрите на
`connections_failed_lru` и `allocated_buffer_bytes`. Если понадобится видеть
причину каждой эвикции, в `S99teleproxy` можно временно дописать `-v 2` —
тогда в логе появится строка вида:

```
check_all_conn_buffers(): closing connection 12 (idle 41.3s) because of ...
```

## Откат

Откат — установщиком с указанием версии релиза с GitHub, а не копированием
файлов:

```sh
VERSION=1.0.5 sh install-keenetic.sh
```

Пока релиз 1.0.6 не опубликован (до проверки на роутере), откатиться можно
установкой локального `.ipk` прежней версии через `opkg install`.

## Известное ограничение

Строка версии внутри бинарника собирается из `git describe` в WSL, где git
считает каталог «dubious ownership» и возвращает пусто, поэтому в статистике
будет `teleproxy-unknown ...`. На работу не влияет, версия пакета — в opkg.
